# 找商品项目需求演进与案例记录

整理日期：2026-11-13（Asia/Shanghai）

这份文档用于把项目从“图片搜同款插件”逐步发展为“买手自动化工作台”的过程讲清楚。内容按时间记录用户当时提出的问题、背后的业务原因、形成的产品决策和后续影响，适合作为项目案例、需求复盘和内部培训材料。

文档只保留功能、问题、流程和验收相关内容，不记录打包、上传、版本递增或发布成品的操作。历史对话中出现过的账号、密码、OAuth 密钥和测试凭据全部省略。

## 项目目标

项目要解决的不是单一的“以图搜商品”，而是一条完整的买手工作链：

1. 用户从抖音商品链接或运营表导入商品。
2. 软件读取商品主图或商品页面图片。
3. 使用主图在网商园、17 网、青创网和衣衫汇等供应商平台搜索候选。
4. 由视觉模型比较商品结构和款式，再由人工确认关键同款关系。
5. 打开已确认的供应商页面，获取货号、店铺、价格、颜色、尺码、成分和商品图片。
6. 通过淘宝/天猫套图或商品采集流程补充资料。
7. 对互拓已有商品做查重，确认没有重复后整理到互拓草稿或待审核流程。
8. 让每一款商品都能在在线表和本地流程中追踪当前步骤、异常原因和人工待办。

项目的核心约束是：自动化要尽量减少买手重复操作，但任何会导致错款、错供应商或重复建商品的步骤，都必须保留证据和人工控制点。

## 时间线

### 2026-10-26：从浏览器插件走向本地工作台

最早的需求是检查现有图片比对插件，并判断是否适合继续扩展。用户提出“过一下这个文件夹”，随后重点关注三个问题：

- 这个功能能不能做成 Electron 应用，与网页插件配合，把主要计算放在本地；
- 未来可能一次处理几百张商品图，多图批处理会不会卡死、内存是否可控；
- 当前程序到底有没有真正做图片比对，还是只把图片下载下来展示。

当时用户明确表达了一个产品判断：如果识别失败，软件就失去主要价值，因此不能只做“图片抓取器”，必须确认视觉模型确实参与比较，并且能够理解多张图片中的款式细节。

这一步形成了两个长期决策：

1. 桌面端负责任务队列、本地图片、模型调用和恢复状态，浏览器插件负责复用用户登录态及平台页面能力。
2. 早期不直接让模型自动决定所有结果，而是让人工看到模型依据并纠正模型，等规则稳定后再考虑减少人工。

也就是说，项目从一开始就不是追求“完全无人值守”，而是先建立可解释、可回看、可人工接管的流程。

### 2026-11-03：明确内部 ERP 上架软件的边界

用户开始描述内部 ERP 上架软件，希望由大模型主导填写商品资料。这里出现了一个重要的范围划分：

- 商品页面爬取、资料整理、字段映射和草稿生成属于当前软件；
- 最终刊登动作不一定由当前软件承担；
- ERP 后续会提供草稿箱，因此软件可以先把资料保存为草稿，让用户在草稿箱中确认。

这样设计的原因是，商品上架存在较高的业务风险。模型即使能整理出大部分字段，也可能在供应商、价格、成分、尺码或商品类型上出错。如果直接发布，错误会立即进入业务系统；保存到草稿箱，则可以把自动化效率和人工审批结合起来。

用户还要求继续检查三个方面：

- 操作步骤是否过多，买手是否需要反复填写相同内容；
- 大量商品同时处理时界面是否卡顿；
- 新用户是否能通过使用教学理解“从哪里开始、卡住后怎么办”。

因此，草稿箱后来不只是一个接口，而是被当成流程中的人工确认节点。

### 2026-11-04：验证 ERP 草稿箱和资料保存流程

这一阶段围绕 ERP 草稿相关接口进行测试。用户看到草稿查询接口返回“页面不存在”或业务码异常，询问这些接口到底是做什么的；随后要求继续测试上传和保存接口，并提出：

- 软件中要能同步查看草稿箱；
- 用户可以同时查看多个商品草稿，判断资料是否满意；
- 人工确认后，再从软件发起后续上架或进入互拓流程。

这里的实际业务原因是，买手不可能只依赖一张结果表判断商品是否可用。用户需要查看草稿中的完整资料和图片，比较多个商品后再做决定。因此后续流程需要同时保存：

- 原商品来源；
- 供应商候选和商品图片；
- 模型整理出的字段；
- 人工修改和确认记录；
- ERP 草稿或待审核记录。

这也是后来“商品流程详情”的基础：一款商品不能只显示一个最终状态，而要能回到它的每个证据和处理步骤。

### 2026-11-04 至 2026-11-06：把买手自动化主链路串起来

用户提出把买手项目与现有工具整合起来，补足淘宝以图搜图获取套图地址的步骤。最终设想的主流程是：

1. 用户输入抖音商品链接或运营表链接。
2. 软件下载抖音商品主图，优先使用第一张主图作为搜索图片。
3. 在四个供应商平台搜索同款或相似款。
4. 展示候选商品、平台来源、商品图片和匹配依据。
5. 人工确认供应商同款后，再采集商品详情和全部图片。
6. 将资料整理到互拓草稿或待审核流程。

用户特别强调“人工占比需要很少”，但并没有要求所有环节都直接自动通过。供应商可能有同款、相似款、不同色或完全不同款，模型不应强行选一个结果。更合理的策略是：

- 模型负责初筛、排序、提取证据和标记风险；
- 人工只处理模型不确定、多个供应商冲突、价格冲突、资料缺失和同款确认；
- 某一款出现异常时打标签并暂停该款，后面的商品继续运行。

用户确认的业务终点是“资料完整后进入互拓待审核，异常项留待处理”，而不是自动发布到线上。这一决策降低了错误商品直接进入生产系统的风险，也让模型可以逐步接管重复性工作。

### 2026-11-05 至 2026-11-06：在线表和账号配置的产品化

用户不希望买手使用复杂的技术配置，因此提出了多次界面和权限调整：

- 普通用户不应看到 API 地址、租户、OAuth client-id、密钥等技术字段；
- 公共连接参数放在服务器侧管理；
- 普通用户只需要填写或关联自己的互拓账号密码；
- 所属公司不应成为使用前的必填项；
- 在线表由自有服务器提供，不依赖外部表格服务令牌；
- 只有管理员可以创建表格，普通用户负责查看、编辑和确认。

这样做的原因是，买手软件的用户是业务人员，而不是开发人员。让业务人员填写 OAuth 参数会增加配置错误，也会让敏感信息出现在不该出现的界面。账号配置最终需要分成两层：

- 管理员/服务器层：维护公共 ERP 连接和权限边界；
- 买手使用层：只处理自己的业务账号和商品任务。

在线表的需求也逐渐明确：

- 可以多人同时查看和修改；
- 行可以持续增加，不预先限制固定行数；
- 只有链接列决定这一行是否算商品，其他字段允许为空；
- 能导入和导出 XLSX；
- 能按链接、表格编号或互拓编码查找并跳转；
- 每次修改产生历史记录；
- 误删除时可以回档；
- 人工确认后才允许自动任务推进。

这实际上把在线表从“数据录入表”升级成了买手任务控制台。

### 2026-11-06 至 2026-11-08：从业务文档提炼人工和自动化边界

用户要求把抖音链接上架、运营表上架和互拓资料编码流程放在一起检查，确认哪些已经实现、哪些适合自动化批量完成。

复盘后，流程被分为三类：

#### 可以自动化的部分

- 从分享文案中提取真实商品链接；
- 下载商品主图和页面图片；
- 调用四个平台进行搜图；
- 保存候选、平台、链接、价格和商品图片；
- 调用模型提取货号、颜色、尺码、成分等页面事实；
- 将页面事实映射到 ERP 字典和草稿字段；
- 对未完成任务进行有限次数自动重试；
- 对在线表进行任务状态回写。

#### 必须保留人工的部分

- 判断候选是不是同一个具体款式；
- 多个供应商都声称相似时选择来源；
- 确认图片缺失或模型无法看清的关键细节；
- 确认价格、成分、尺码或供应商名称的冲突；
- 确认互拓已有商品是否应关联，而不是重复新建；
- 确认草稿是否可以进入待审核。

#### 失败时不能做的事

- 不应把“没有返回结果”当成“没有同款”；
- 不应把模型的相似款当成已确认同款；
- 不应在 ERP 查重失败时继续创建商品；
- 不应在平台需要登录或验证时自动重复提交可能计次的请求；
- 不应因为某一款失败而阻塞整批商品。

### 2026-11-08：自动买手从“能跑”进入“可恢复”

用户连续反馈自动任务停在第一步或第二步：

- 浏览器没有平台登录记录；
- 插件没有更新或没有连接；
- 链接前面有文字，程序没有自动提取中间的真实链接；
- 第二步卡住后没有继续或重试按钮；
- 多商品处理时不知道哪些成功、哪些失败。

这些问题说明，自动化程序不能只显示“处理中”或“失败”，还要告诉用户下一步是什么。于是流程界面需要记录：

- 当前步骤；
- 卡住原因；
- 是需要登录、更新插件、人工判断还是等待平台回调；
- 可以执行的主操作；
- 该操作会推进到哪一步；
- 单件失败是否会影响后续商品。

用户还要求来源链接的所有图片放到人工复核区，因为单张主图经常看不到后背、袖口、尺码图、口袋或装饰细节。由此形成“来源图集 + 候选图集 + 人工确认”的复核结构。

### 2026-11-09：识别结果页从列表变成审核驾驶舱

用户对识别结果页做了完整审计，认为问题不是简单的候选太多，而是三个层级混在一起：

- 平台抓到了多少候选；
- 模型给了多少建议；
- 人工还有多少任务没有处理。

因此用户要求首屏改成处理状态驾驶舱，而不是突出总候选数。核心要求包括：

- 默认先看推荐候选；
- 低分候选进入已排除；
- 未识别候选进入需重试；
- 每条结果显示平台来源和搜索类型；
- “模型建议”“人工确认”“待人工核对”分开统计；
- 颜色不同不能单独判为不同款；
- 判断重点是品类、廓形、领口、门襟、袖型、口袋、下摆、拼接、图案位置、纽扣和装饰；
- 人工动作改为确认同款、排除候选、无法判断；
- 匹配分只作为排序参考，不强迫人工重新填写分数；
- 每个状态只提供一个清晰的下一步。

用户随后补充动态排除规则：当最高相似度达到90分以上时，可以剔除85分以下；最高分在85分左右时，可以剔除70分以下；模型请求失败自动重试3次，仍失败后由人工点击，再开启下一轮3次自动重试。

背后的原因是，审核页面的目标不是展示模型做了多少计算，而是帮助买手快速完成决策。排序、状态和下一步必须围绕人工任务设计。

### 2026-11-09 至 2026-11-10：四平台搜索覆盖和真实采集验证

用户担心软件可能只搜到了网商园，却把结果误认为四个平台都搜过。因此要求：

- 显示每个平台的总候选数、实际返回数和可用数；
- 显示平台是否搜索完成、是否需要登录、是否发生权限/额度/超时异常；
- 确认青创网为何不稳定；
- 确认四个平台是否都能拿到商品信息；
- 在已登录状态下用真实服装页面验证商品标题、货号、店铺、价格、颜色、尺码和图片。

这一步形成了一个重要的证据边界：

- 平台页面规则测试通过，不代表所有真实账号、所有商品模板都能稳定采集；
- 搜索完成不代表候选一定正确；
- 页面打开不代表主图、详情图或商品字段已经获取；
- 某个平台失败不能覆盖其他平台的成功结果；
- 对计次搜图请求，超时后不能盲目自动重放。

### 2026-11-11：资料事实、平台来源和商品流程

用户通过真实页面截图发现三个数据问题：

1. 页面已有成分、颜色、尺码等信息，但软件表单没有正确填写；
2. 软件里供应商名称与当前商品页面不一致；
3. 青创网候选显示145元，但当前网商园商品显示150元。

解决这些问题时需要明确“当前供应商事实”和“其他平台候选参考”是两套数据：

- 当前选中的网商园商品，其供货价和店铺应来自网商园页面；
- 青创网145元只能作为另一个候选平台的价格参考；
- 不能因为候选更便宜，就把它覆盖成当前供应商成本；
- 每条价格必须带来源、商品链接和平台标签。

用户同时提出把软件改成“按商品流程管理”：

- 一款衣服对应一个任务和一个本地商品文件夹；
- 表格的一整行可以打开这款商品的流程；
- 详情页显示当前在哪一步、为什么停住、下一步是什么；
- 处理完成后返回原表格并定位原行；
- 弹窗关闭按钮、返回表格按钮和流程导航始终可见；
- 候选图片区域不能留下大块空白，要让人工真正看到图片。

背后的原因是，买手处理的是商品，而不是一条孤立的接口请求。任务、图片、供应商、草稿和人工决定必须围绕同一个商品聚合。

### 2026-11-12：成分、真实尺码图和 ERP 查重

用户发现供应商页面实际上有成分属性“面料：聚酯纤维”“填充物材质：聚酯纤维”，但软件仍然显示为空。原因是旧规则要求“成分名称和百分比同时存在”，没有百分比就把整项丢弃。

新的业务规则是：

- 页面明确出现的成分名称必须保留；
- 百分比缺失时显示名称，并明确提示比例待人工核实；
- 不能把“聚酯纤维”自动猜成100%；
- 面料、填充物、里料要分开保存；
- 人工只补页面没有提供的真实比例。

用户还要求尺码图不能用文字下拉框代替真实图片，因为人工需要看图确认表格内容。于是尺码图流程改成：

- 从真实商品图片中显示缩略图；
- 人工点击选择；
- 可以放大查看；
- 图片加载失败可以重试；
- 未选择时不默认第一张商品照片；
- 窄窗口下图片区内部滚动，不影响表单和关闭按钮。

同一阶段发现互拓商品池查重超时。只读检查显示 OAuth 和权限正常，但 `POST /erp/pool-product/page` 在大商品池下响应很慢，部分请求返回业务码500；客户端原有等待时间又会先断开。用户说明“商品多导致慢是正常的”，因此后续重点从“是不是账号坏了”转为“等待时间和响应契约是否合理”。

### 2026-11-12：互拓同款改为图片优先、编码辅助

用户提出互拓同款判断的新要求：互拓候选必须有商品图片和商品编号，并与供应商商品做匹配。用户给出了编码示例：

`GZ-休闲裤-1HYFS-K2028JR`

拆解规则为：

- `GZ`：广州；
- `休闲裤`：商品类目；
- `1HYFS`：供应商缩写；
- `K2028JR`：供应商货号。

其他地区前缀包括：

- `QZ`：泉州/石狮；
- `CS`：常熟；
- `JX`：嘉兴。

用户特别强调，不同地区的供应商可能生产同一个款式，货号也可能不同，因此不能用编码差异直接判不同款。合理的判断顺序是：

1. 先比较商品图片中的款式和结构；
2. 再解析商品编码，辅助判断来源、类目、供应商和货号关系；
3. 模型只给建议，不自动关联已有商品；
4. 图片缺失时禁止仅凭货号关联；
5. 人工确认同款后关联已有商品，确认不同后才继续新建。

这一步把“ERP 查重”从简单的货号检索提升为“候选召回 + 图片证据 + 人工决策”的流程。

### 2026-11-12：ERP 慢查询的诊断和等待优化

用户看到 `productNo` 查询没有有效列表、`articleNo` 查询出现HTTP503，要求列出原因并尝试修复，无法修复时给内部工程师说明。

排查得到的原因分为两层：

- 代理层：云端代理原先等待上游30秒，后调整到55秒；用户后续重试约58秒仍失败，证明55秒仍不够；
- ERP 接口层：商品池查询可能存在慢查询、业务码500或返回结构不符合客户端预期，不能把异常响应当成“没有同款”。

用户随后明确授权部署和发布，形成的修复策略是：

- 云端代理等待提高到110秒；
- 客户端查重专用等待提高到115秒；
- 每页从100条降到10条，最多取3页，减少单次响应负担；
- 接口返回结构异常时，只显示安全的类型和字段名，不记录敏感字段值；
- 代理超时使用明确诊断码；
- 查重失败仍暂停新增，不绕过查重继续创建。

这体现了一个重要的工程原则：可以通过延长等待和减少请求规模缓解慢查询，但如果 ERP 仍返回业务500或结构不符合契约，就必须由 ERP 维护人员检查筛选条件、数据库查询和响应格式。

## 项目决策总结

### 为什么没有直接做成完全自动上架

因为同款判断、供应商选择、成分比例、价格来源和 ERP 查重都存在业务风险。模型可以减少检索和整理工作，但不能在证据不足时代替人工承担商品错款和重复建款的责任。因此项目采用“自动提取和排序，人工确认关键节点”的渐进路线。

### 为什么要把图片放在流程顶部

服装同款判断不能依赖标题或货号。颜色可能不同，拍摄角度也可能不同，但领口、门襟、袖型、口袋、下摆、拼接、图案位置和装饰结构通常更有判断价值。人工需要同时查看来源图、候选主图和详情图，才能确认模型是否判断正确。

### 为什么要把在线表做成任务控制台

用户处理的是一批商品，每一行商品都可能处于不同阶段：等待平台登录、候选待审核、供应商资料缺失、ERP 查重失败或已经进入草稿。只有把表格行、商品文件夹、任务状态、图片证据和处理记录绑定起来，用户才能知道某一款下一步该做什么。

### 为什么失败时必须暂停而不是继续新增

当 ERP 查重接口超时或返回结构异常时，系统并不知道“没有同款”，只知道“没有得到可靠结论”。如果此时继续创建，就可能重复建商品。因此系统宁可停在待处理，也不能把异常伪装成空结果。

### 为什么要区分模型建议和人工确认

模型分数适合排序，不等于业务确认。把“模型建议10条”写成“有效结论10条”会让用户误以为已经确认。项目后来明确拆分：模型建议、人工确认、待人工核对、需重试和已排除，每种状态都有独立的下一步。
