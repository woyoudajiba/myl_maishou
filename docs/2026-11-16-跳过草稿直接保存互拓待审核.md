# 跳过草稿直接保存互拓待审核

日期：2026-11-16。

后续发布状态：本功能已随 `26.11.16-v2` 完成客户端、配套插件及正式云端代理发布；下文保留实现阶段的证据与边界，最终交付见 `2026-11-16-v2-打包与部署验收.md`。

## 用户确认的流程

正式互拓草稿查询返回 HTTP 200 / 业务码 501。用户确认“不用草稿，直接上”，按此前约定解释为直接保存到正式互拓的“待审核产品”，最终审核上架继续由内部人员在互拓完成。

调整后的新任务流程：读取来源图片 → 四平台核对供应商 → 取得供货资料 → 人工确认淘宝套图 → 互拓采集 → 整理资料 → 直接保存待审核并回填商品编码。

## 实现

- 使用正式网页现有的 `POST /erp/product-addition/add` 保存完整商品资料，跳过 `/erp/product-draft/add` 和草稿转换。
- 新任务创建 `productAttempt` 固定完整请求正文、商品编码及本机提交检查点编号；编码由仓库、类别缩写、供应商缩写、供应商货号组成。
- 发出新增请求前持久化 `productSubmission`。该接口没有已确认的幂等保证，不把本机编号描述为服务端幂等键，也不因超时自动重复新增。
- 保存成功回执的 `data=0` 仅表示接口受理，不能作为产品 ID。随后按完整 `productNo` 和 `articleNo` 限定查询，核对唯一匹配的供应商，再按真实产品 ID 回读详情。只有商品身份相同且 `productState=0` 才完成并同步互拓编码。
- 网络失败、业务拒绝、程序中断、无法查到原记录、列表不完整、多条匹配或回读身份冲突均保留原提交。已有提交的任务点击重试进入只读核验，不重发新增。
- 不进行图片同款查重，不遍历整个产品池；这里的限定查询只用于确认本次写入回执。最终重复商品仍由人工在互拓处理。
- 草稿入口默认隐藏；有历史已保存 draftId 的任务仍保留入口与旧回执，不自动把草稿转换为新的直接提交。旧视图恢复到隐藏草稿页时回到买手工作台。
- 页面流程名称、说明及最后阶段改为待审核；保持现有布局。资料缺失、供应商不能唯一对应时仍先处理例外，不填造供应商信息。

## 网关能力

新增允许路线 `/erp/product-addition/add`，默认关闭，使用加密设置 `directSaveConfirmed` 或服务器 `ERP_DIRECT_SAVE_CONFIRMED` 明确启用。客户端通过 `/erp-config/me` 的 `canSavePending` 获取能力；旧的草稿写入开关不替代此开关。

受控部署脚本增加 `--enable-direct-pending`，随已验证网关发布时保存启用状态。脚本仍保留原账号映射、密钥、正式地址与备份回滚规则，本身不创建商品。没有放开审核、通知或最终上架路线。业务 401 的授权刷新保留，新增请求仍不自动重放。

## 真实状态和发布边界

本轮完成源码调整与隔离验证，没有打包发布新客户端、没有部署本轮直接保存网关、没有向真实 ERP 新增产品，也没有调用付费模型。与前两次云端修复不同，这次客户端提交路线及持久化状态均改变，必须发布安装新版客户端，并同步启用网关的直接保存能力后才会生效；当前已安装的 26.11.16-v1 仍是原草稿流程。

本机 D2603 已从采集推进到 mapping，但目前显示“供应商未唯一对应互拓档案”，没有 draftId。因此该任务可以在升级后沿用已有采集资料，待供应商准确对应后走新流程；本轮没有更改其真实任务或替用户选择供应商。

正式草稿问题的只读证据保存在 `draft-501-evidence.json`、`draft-501-method-account.json`、`draft-501-direct.json`。两个账号和绕过代理的查询均表明列表、详情路线返回 501；普通类目读取正常。接口文档明确要求草稿功能分支及数据库迁移，是否未部署或路由未配置仍需 ERP 内部确认。本次新流程不再依赖它。
